01 · The thesis

Singularity Flow — Architecture Guide

For architects and technical evaluators: how the system works, where the tokens go, what is genuinely different, and where it extends. Companion to the full Deep Dive; this is the load-bearing subset.

One sentence: a Git-native lifecycle kernel in which a probabilistic layer (models) may propose, draft, and narrate, and a deterministic layer (a zero-dependency Node CLI) exclusively validates, transitions, commits, publishes, and recovers — so AI participates everywhere and is the authority nowhere. The model’s statement never changes lifecycle truth; the kernel’s checks do.

Freedom of process

Workflows are not fixed product shapes — teams create new work types by composing phases in workflow.yml: reviewed like code on sflow/config, pinned like law at story start, constrained only by the monotone fold (you can tighten the floor, never dig under it). A new rail is a pull request, not a platform release.

Freedom of motion

Developers enter and leave the loop at will: close the laptop mid-anything — legally, silently; return on any machine with story continue and the loop resumes exactly where truth left it. The interval governs boundaries, never keystrokes; the system waits, it never chases.

Read it as an operating system: every surface is a shell over the same kernel — none holds private truth, all speak the same envelope, and the subject index gives each the same resolution of “which story am I looking at.” The model lives in user space with the other shells; human authority sits above the diagram, not inside it — the kernel enforces that consent flows down as exact typed confirmations and never gets synthesized below. There is exactly one write path into persistent authority, and it is the transaction in section 03.

02 · State authority

Git is the database — deliberately

Lifecycle state lives on the work-item branch: singularity/work-items/<ID>/ holds workflow.json (the authority), artifacts, approvals, pinned context, telemetry, and evidence. Derived files (STATUS.md, reports) are projections — regenerable, never authoritative. Local session data only selects the active subject.

PlaneBranchRole
Application codemain + feature branchesWhat ships
Approved configurationsflow/configLaw — copied byte-for-byte to each story at start
Lifecycle statesingularity/work-items/*Operational authority per story
Evidence mirrororphan state branchAppend-only ledger · governed world model — proof, never read/write authority

Frame invariance: CLI, VS Code, Copilot, and any fresh clone compute the same truth from the same refs — no daemon, no server, no cache with authority. A reviewer’s entire onboarding is git clone.

03 · The core mechanism

Publication as a transaction

Every governed mutation crosses one boundary with the same guarantees:

1  verify branch, HEAD, state revision (+ disk-bytes fingerprint —
   catches uncommitted foreign writes, not just moved refs)
2  refuse if a pending publication exists (recovery first)
3  apply the deterministic transition · validate invariants
4  stage ONLY allowlisted governed paths (your scratch never enters)
5  one isolated commit (isolated index — your staging untouched)
6  advance the branch by compare-and-swap · push without force
7  on failure: journal under .git/singularity-flow/ →
   `sflow sync` replays exactly once · races refuse, never clobber

Concurrent same-subject writers are serialized by a PID-safe subject lock (atomic-rename reclaim). The property that falls out: kill anything at any moment — a dead laptop or Ctrl-C leaves either nothing or a journaled, exactly-once-recoverable step. Retry is replaced by recovery.

04 · Time control

Pins and the monotone policy fold

At story start, the effective policy is computed once — fold(workflow defaults → work-type overrides → capability constraints root→leaf) — where later layers may tighten but never weaken (protected paths union; approval floors hold; a capability’s self-approval ban cannot be re-allowed downstream). The folded result, templates, agents, and budgets are pinned: hashes recorded, config bytes copied to the story branch. In-flight work is immune to later edits; escalation ladders are pinned too and only ever strengthen. The same monotone one-way rule appears at three altitudes — the protection boundary, the policy fold, the escalation ladder — which is why delegated configuration is safe.

06 · The skill layer

Skills, SKILL.md, and the loop

A skill is the only doorway between conversation and kernel: a folder with a SKILL.md body, a registry entry assigning one of six behavioral contract classes (relay · review · guided · selection-gated mutation · clarification+artifact · conversational), and the CLI command it wraps. Contract text and token policy are mechanically stamped into every body; check (463 validations) fails on drift, orphans, or bodies over the ceiling (warn 500 · fail 800 tokens). Only three conversational skills are session-indexed (~14 tokens each — the ≈42-token login); the other 94 demand-page on invocation.

you      /sflow-status PAY-1187
host     loads SKILL.md (first use) → model emits the tool call
kernel   child process · resolves subject · reads state · zero tokens
result   envelope: output + why[] + next[] (preview + handle if large)
model    relays under contract · surfaces NOW/THEN
event    structured conformance record → checkers score the contract

The governed loop (/sflow-continue) cycles WHERE-AM-I → CLARIFY → GENERATE → PUBLISH → VERIFY → NEXT: the kernel owns the loop; the model fills exactly one slot (generation) and narrates the rest. It stops loudly at every human boundary, and any arrow is a safe place for a session to die — state is on the branch; the next continue, on any machine, re-enters where truth left it. Mutations ride the action envelope (kernel-computed, content-hashed, revision-bound, one action per execution), so an invalid call is unexpressible rather than caught. The invariant every new skill inherits: the skill layer can make the kernel easier to ask — it can never make it possible to bypass.

07 · Freedom of motion

Suspension and resumption without loss of governance

The system's most consequential human property: a developer may leave the loop at any moment and re-enter it at any later moment, on any machine, without notice, without penalty, and without weakening a single guarantee. This is possible because governance is applied at the boundaries of work, not during it.

MomentWhat happensWhat preserves governance
Entering a work phaseAn interval baseline pins itself: source-base commit, specification and policy hashes, protected paths, required checks, escalation ladderThe contract is fixed before freedom begins — later configuration changes cannot alter it
During the intervalAny editor, any assistant, any commit style, online or offline. No check-ins, no narration, no mandatory checkpoints, no timersNothing needs supervising, because nothing during the interval can mutate lifecycle state — mutation requires the kernel transaction
LeavingClosing the laptop with no command is a legal, recorded-free exit. Optionally: checkpoint (local — may be dirty, honestly labeled machine-local) or checkpoint --published (clean tree, remote reachability verified before durability is claimed); pause --publish for handoffsCheckpoint records state what they can prove and no more; pause duration is never exported or evaluated
Returning — any machinestory continue rebuilds the continuation packet: PINNED (the contract), SINCE YOU LEFT (observed changes, clearly separated), STALE, and the valid next actionsContract and drift are never blended; the packet is computed from the branch, so every machine derives the same truth
The boundaryBefore submission, reconcile deterministically compares reality against the baseline; a human assigns meaning through a recorded disposition — including correcting the plan while keeping the codeVerification concentrates at the crossing point: evidence bound to the exact commit, protected-path and policy predicates evaluated, escalation along the pinned ladder with all work preserved

The design argument: continuous oversight and durable governance are separable. Because state authority is in Git and mutation is transactional, the interval requires no observation to remain safe — and the boundary check is stronger than continuous supervision would be, because it is deterministic, reproducible, and bound to exact content. The result is a process that is simultaneously stricter at its checkpoints and freer between them than conventional practice.

08 · Where the tokens go

Token economics, measured

The design rule: cost scales with governed work, never with sessions. The overwhelming majority of operations — gates, transitions, planning, status, composition, recovery — are deterministic kernel code: zero tokens, milliseconds, provably model-free (CI runs a complete story lifecycle with fake model executables on the PATH).

SurfaceConventional always-loaded designSingularity Flow
Session fixed cost~1,400 tokens (full catalog at every login, used or not)≈42 tokens — 3 indexed skills × ~14; the other 94 demand-page on invocation
Structural questions5–15k tokens of exploratory file reading≈172-token bounded code-graph query (blast radius, dependencies)
Large resultsFull report pasted into context; cache invalidatedDeterministic preview + revision-bound handle; show --section expands on demand; transcripts stay append-only and cache-valid
GroundingWhole world model, every phasePhase-declared views, tiered (full/brief), budgeted per phase with refusal-before-invocation; three measurements recorded (candidate / selected / final prompt) so savings claims can’t inflate
Latency floor—≈97 ms cold CLI start (lazy dispatch); ≤150 ms reads, CI-enforced budgets

Accounting is exact where the host supplies it and labeled unavailable otherwise — never estimated; measurement method travels with every number.

Why kernel operations cost zero — in detail

The majority of platform operations are questions about state or transitions of state: which phase is current, which gates pass, what actions are legal, which approvals bind which hashes, how to recover a failed publication, what a story's history is. These are computations over files and Git refs — there is no linguistic content in them, and therefore no theoretical reason for a language model to participate. The kernel executes them as ordinary Node code: file reads, hash comparisons, set arithmetic, graph walks. Token cost: zero. Latency: milliseconds (≈97 ms cold, less warm).

When such an operation is invoked through the conversational surface, the only tokens spent are interface tokens: the skill body on first use (bounded by the stamped ceiling) and the bounded relay of a result preview — typically tens of tokens wrapping an operation whose own cost is zero regardless of its complexity. An eight-gate submission check and a one-line status query cost the same: nothing. The composition step that prepares a generation is itself L0 — the kernel assembles pinned templates, views, and inputs deterministically, so tokens are spent only on the single step that is genuinely linguistic: the model drafting the artifact.

Three consequences follow. First, cost scales with governed creative work, never with team size, session count, or curiosity — status checks, planning, review preparation, and recovery are free at any frequency. Second, the zero-cost core is what makes routing everything through the kernel affordable: a transaction that cost tokens would be bypassed; one that costs milliseconds becomes a habit. Third, the claim is enforced rather than asserted: every zero-token operation is classified model: never in the operation registry, and CI runs the complete lifecycle with model executables replaced by tripwires — any deterministic path that attempted a model call would fail the build.

09 · Theoretical minima

The irreducible cost model

Each cost dimension of governed delivery has a theoretical lower bound. The architecture is designed to approach these bounds and to make the remaining cost explicit and inspectable. What remains at the bound is not overhead — it is the substance of governance itself.

DimensionTypical additional costIrreducible minimumMechanism that approaches it
TokensAlways-loaded catalogs; results re-entering context; whole-model groundingZero for deterministic truth; information content of the artifact plus required grounding for creationL0 kernel operations; demand-paged skills; reference previews; phase-budgeted views
Human ceremonyCoordination and reporting activity not tied to a decisionOne human act per non-delegable decisionApproval boundaries as configuration; policy waivers move consent upstream into reviewed policy
Cycle timeProcess latency between decision pointsAuthoring time plus one review latency per approval boundaryMillisecond kernel operations; receipts isolate approval wait as the dominant residual
Durable stateParallel records, copies, and secondary systemsThe worldline: decisions, identities, and content hashesGit as sole authority; all other views are regenerable projections
User knowledgeProcess documentation held in memoryOne command plus the judgment of the rolenextsteps and the narration contract surface the process at the moment of need
TrustReliance on process having been followedThe hash function, the configured identity assurance, and reviewer attentionEverything else moves from the trusted column to the verified column

The consequence for evaluation: measured cost above these minima indicates removable inefficiency; measured cost at these minima is the definition of the governance being purchased. The impact framework reports both, with the measurement method attached.

11 · The evidence plane

Claims vs. proof, kept separate

Every consequential object is content-addressed and joined: artifacts, inputs, approvals (identity + authority + artifact SHA-256, stale-on-edit), checks bound to exact commits, clause claims (spec trace: requirement → claim → commit → test → approval), MCP tool outputs, visual pixel evidence, and per-story Impact Receipts — deterministic, completion-commit-bound, reproducible by impact verify, compared in pre-registered studies that label results validated quality-gated gain vs. observed acceleration and refuse cohorts below the privacy floor. The append-only ledger verifies from a bare clone, offline. Mechanical coverage never claims semantic correctness; judgment and evidence are both retained and never confused — the honesty gradient (exact · derived · self-reported · unavailable) is schema, not style.

13 · The authoring surface

Bringing things in — agents, skills, artifacts, workflows, world model

Every kind of capability enters through the same pattern: plain files, brought from anywhere Git or HTTPS can reach, admitted through a validation gate, then pinned and governed like everything native. Nothing imported can acquire authority.

WhatHow it comes inGate it passes
AgentsMarkdown personas (.agent.md: role, declared tools, world-model views) — authored locally, copied from any repository, or mapped onto existing Copilot agent definitions the host already runsComposed deterministically, hashed, pinned per story; tool declarations cross-checked against MCP policy; an agent role is never an authorization role
SkillsA folder plus a registry line — portable by construction (zero-dependency files), so a skill authored in any repository or fetched from any URL drops in unchangedMechanical contract stamping; token ceilings; the full check validation set; slash-only unless deliberately indexed
Artifacts & documentsLocal files via documents upload / inputs add; remote artifacts fetched by URL (HTTPS-only, credentialed URLs rejected, redirects re-validated, size-capped)Hashed before use; persisted source URLs stripped of query and fragment; forged lifecycle metadata inside imported files removed; written only to pinned paths
WorkflowsWork types composed as phases in workflow.yml — created, copied between repositories, or evolved like any configurationReview branch and pull request onto sflow/config; schema validation; the monotone policy fold (may tighten inherited constraints, never weaken them); pinned per story at start
World modelBuilt deterministically from the repository (or extended progressively per view); published to the governed state branchInjected into prompts only as phase-declared views under byte budgets — never wholesale; version-pinned, staleness surfaced as warnings; grounding is optional, never a lifecycle precondition

Git-workflow compatibility is by construction, not adaptation: stories are branches created from the team’s normal base; developers commit in their own style; pull requests, protected branches, code review, and CI operate unchanged — the kernel adds its lifecycle commits through the same Git it found, touching only allowlisted governed paths in isolated commits. Existing branching models (trunk-based, GitFlow, fork-based) require no modification; the platform’s three additional branches (sflow/config, work-item state, the evidence branch) live alongside them without intersecting application history.

Completeness runs both directions: every feature decomposes into these — heal is gate + contract + generation + transaction; autopilot is the planner iterating transactions until an approval; impact is records + pins + arithmetic; a waiver is an approval moved upstream into a pinned policy — and none of the eleven decomposes further within the platform’s vocabulary. Remove any one and a named guarantee dies with it. This is the complete ontology: fourteen sections of architecture, spelled with eleven words.

15 · The invariants
