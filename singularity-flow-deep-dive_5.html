Platform at a glance

The quickest route to understanding Singularity Flow is to separate the authoring surface from the lifecycle engine and the lifecycle engine from its state substrate.

The shortest accurate description

Copilot proposes content. The Node.js runtime assembles governed context and controls lifecycle transitions. Git carries the shared state. Humans make governed choices and approval decisions.

The platform deliberately places probabilistic reasoning at the edges. A model may interpret an ambiguous request, ask questions, draft a requirements document, or explain a deterministic result. It does not own the phase state machine, approval authority, artifact hashes, publication, or recovery. Those responsibilities remain in conventional code and Git.

This separation is the organizing idea for every subsystem described in this guide. It is also the reason the platform can expose the same lifecycle through a terminal, Copilot, and VS Code without allowing any surface to become a second source of truth.

02

The governing design principle

The model is an interpreter and authoring assistant; the kernel is the execution engine.

The probabilistic side

  • Interprets human intent and asks free-form clarification questions.
  • Uses a phase-specific governed agent and a named skill playbook.
  • Drafts requirements, designs, implementation summaries, verification evidence, and conformance analysis.
  • Explains deterministic status, reports, next actions, warnings, and failures.
  • May be replaced, cleared, compacted, or changed without losing lifecycle truth.

The deterministic side

  • Resolves the active Story or Initiative and immutable configuration snapshot.
  • Selects the legal next actions and enforces sequence gates.
  • Verifies world-model grounding, approved inputs, artifact integrity, identity, and authority.
  • Writes lifecycle state, projections, commits, pending-publication recovery, and optional ledger proof.
  • Derives reports, progress, review packets, and the final governance gate.
Containment is scoped, not a sandbox

The current protocol governs Singularity Flow lifecycle mutations. It does not sandbox every shell command or ordinary source edit that a person or coding assistant could perform. Repository protection and server-side validation remain separate deployment controls.

The five invariants that define the platform

I1 · Containment

The model never mutates state; every mutation crosses one deterministic publication transaction. Corollary: model error ⇒ presentation error, never state error.

I2 · Typed boundary

Every skill declares exactly one behavioral contract from a closed vocabulary of six; contract text is stamped mechanically by policy, never hand-copied.

I3 · Session-scaling cost

Fixed per-session context cost is O(conversational skills), not O(total skills): three indexed skills, ≈42 tokens, regardless of how large the catalog grows.

I4 · Disposable sessions

No lifecycle truth exists only in a conversation. Any terminal, editor, or future session resumes from Git; closing a chat loses nothing.

I5 · Evidence

Every generation is attributable to hash-pinned inputs; every approval is bound to the exact artifact hash it covered; every claim above is checkable offline.

05

The stack, read as an operating system

The cleanest mental model for the whole platform is one every systems engineer already carries: a ring-0 kernel, a typed system-call interface, and a user space where probabilistic things are allowed to happen because nothing there can touch state.

Why the metaphor is legitimate rather than decorative

Each mapping is structural, not cosmetic. User-space processes cannot address kernel memory; here, no surface or model can write lifecycle files — the architecture test fails the build if one tries. Syscalls are the only crossing; here, every crossing carries a behavioral contract stamped by policy. The journal survives a crashed process; here, the orphan ledger survives a squashed branch. Nobody calls Linux "a bunch of config files" — the config describes the law, and the kernel enforces it.

06

The boot sequence: how the system comes up, and why it costs nothing

Read the platform's lifecycle as an OS boot and the token economics fall out naturally: everything a real operating system does at boot is free here too — the meter runs only when the user's actual compute runs.

0Flashing the firmware — once, ever. install.sh lays down the CLI, the plugin, and the OTEL wrapper around the copilot binary. The wrapper is the platform's auditd: exact token accounting is recording before any other software runs, which is why every savings number in this document is measured rather than claimed. Zero tokens.
1Partitioning the disk. sflow bootstrap is mkfs: it writes the partition table — workflow.yml, capabilities.yml, portfolio.yml — and creates the journal partition: git worktree add --orphan births the state branch with no shared ancestor, a journal on the same disk but outside the main filesystem's reach. Zero tokens.
2POST and fsck. sflow doctor is the power-on self-test; the governance gate's hash verification is fsck — config matches its pinned snapshot, templates match their SHA-256s, approvals aren't stale. The subject index build is mounting: every story resolvable to the same inode from every surface. All deterministic; the kernel never asks a model whether the filesystem is intact.
3The kernel boots — every time, in milliseconds. The one place the metaphor inverts, deliberately: there is no daemon. Every sflow invocation cold-boots the kernel — read config, mount state from Git, take the subject lock (its PID table), execute one syscall, write the journal, exit. A unikernel boot per command, affordable precisely because the kernel is zero-dependency and zero-token. A kernel that costs nothing to boot is a kernel you route everything through — which is why "all mutations cross the transaction" is a habit, not a tax.
4User login — where the token story used to go wrong. Typing copilot in a governed repo is spawning a login shell. The hook is /etc/profile — a shell command, so ungoverned repos print nothing: no motd, no bytes. The skill index is the shell loading command completion — and this is the reformed sin: it used to load 1,403 tokens of completion data for 38 commands at every login, bloatware in the autostart folder, plus an unconditional prompt hook that was pure startup cruft. Today the autostart folder holds three entries — help, nextsteps, status, 14 tokens each: 42 tokens is the entire cost of logging in (−97%). It was the only cost that scaled with sessions instead of work — the one meter that ran while you slept.
5Demand paging. The other 85 skills exist on disk and occupy zero context until a human types their slash command — then the body pages in (≈230 tokens, once) and stays resident, like any page cache. You never pay for capability you didn't touch. The discipline is the page-size ceiling: bodies warn at 500 tokens and fail at 800, enforced by check — a resident page is rent paid every remaining turn.
6Shared libraries, precompiled. The light world model and the code graph are /usr/lib: built once, deterministically (the amortized L1 layer), then linked into every process free. "Who depends on the publication unit?" is a ≈172-token bounded query against the precompiled graph instead of 3–6 model-driven file explorations at 5,000–15,000 tokens — a 30–80× reduction on exactly the question class implementation sessions ask constantly. Understanding was compiled once; sessions link against it.
7The metered device. Only now does anything cost money: generation is the one metered peripheral (L2). Even here the kernel does the DMA setup free — deterministic composition puts the byte-stable prefix (pinned template, agent, digests) first, so repeat turns hit the provider's prompt cache like a warm TLB at roughly a tenth the price. The model is billed for judgment and prose; everything that positioned it to judge was L0/L1.
8Crash, kill −9, walk away. Close the laptop mid-anything: pending-publication records and the ledger outbox replay on next mount; the CAS ref update means a half-finished transaction either never advanced the branch (unreachable scratch, garbage-collected) or is durable and enters recovery. Sessions are diskless terminals — nothing true lives in them — so ending one costs zero tokens and zero information. Which enables the cheapest trick of all: fresh session per phase — every accumulated page drops, nothing is lost, the next login costs 42 tokens again.
The economics in one sentence

An operating system doesn't charge you CPU to exist — it charges you for your programs. Boot, mount, fsck, login, paging, linking, journaling: all deterministic, all free, all instant. The meter runs only when the human's actual work — the generation — runs, and even that arrives cache-optimized and pre-grounded. The old architecture paid rent per session; this one pays per unit of governed work, the only denominator that should ever have had a price on it.

Subject resolution rules

  1. Explicit reference wins
    A supplied Story or Initiative ID/branch is resolved before local session context.
  2. Registered branch aliases are indexed
    Canonical and child branches resolve to their owning lifecycle subject.
  3. Ambiguity is an error
    If more than one subject matches, the CLI lists candidates rather than guessing.
  4. Creation is explicit
    A missing reference becomes a new ID only inside a creation command.
  5. Ledger evidence is read-only
    The proof plane can identify a subject, but cannot replace a missing lifecycle branch for mutation.

An active Story continues under the exact policy it started with, even if main later changes the workflow, templates, authority groups, or capability map. A configuration edit therefore cannot retroactively relax or tighten an in-flight decision.

Story lifecycle and phase state machine

A Story is a committed aggregate whose current phase moves through a controlled prepare → publish → submit → decide loop.

StatusMeaningLegal direction
not_startedPhase is part of the immutable profile but not yet active.No generation or decision is current.
in_progressThe phase may be prepared/authored and, once valid, published.Current phase only.
awaiting_approvalA submitted generation and review packet are waiting for a human decision.Approve or request changes.
approvedThreshold reached for the exact current artifact hashes.Next phase becomes active or workflow completes.

The durable phase loop

  1. Compose and prepare
    Resolve the current phase, default agent, template, approved inputs, world-model views, remote dependencies, evidence, and task. Create or refresh managed blocks without advancing lifecycle state.
  2. Author
    Copilot or a person edits the governed artifact path. Artifact-only phases are constrained to their phase artifact directory; implementation and verification phases may allow source changes.
  3. Publish generation
    Recheck pending publication, sequence, grounding, inputs, protected paths, write scope, artifact registration, minimum content, placeholders, telemetry, and capability budgets. Then create and push a generation commit.
  4. Submit
    Require a fresh generation, find its generation commit, prove required remote publication, run configured quality commands, validate the artifact again, create the review state, and publish a separate submission commit.
  5. Decide
    An authorized human reviews exact artifacts and packet hashes. Approval may advance the workflow; requesting changes creates a structured change request and reopens an allowed target.

Why generation, submission, and approval are separate

Generation answers:What content was produced, by whom, with which context?
Submission answers:Is that generation complete, checked, published, and ready to review?
Approval answers:Which authorized human accepted that exact evidence?
Typical Story phase commands
# Read-only recommendation
singularity-flow nextsteps ENG-142

# Prepare and publish one generation
singularity-flow prepare design
singularity-flow wm compose --phase design --task "Design the change"
singularity-flow phase publish design

# Create the review state
singularity-flow submit --phase design

# Record a separate decision
singularity-flow approve ENG-142 --fetch
# or
singularity-flow reject ENG-142 --fetch   --to requirements   --reason "Failure behavior is not specified"
Completion is intentionally simple

Progress is the number of approved phases divided by the immutable phase count. The platform does not assign guessed fractional credit to an in-progress or awaiting-approval phase.

End-to-end information flow

The system is easiest to reason about as a sequence of controlled boundary crossings rather than as one autonomous agent loop.

Trace of a phase-generation request

  1. Human intent enters through a surface
    The contributor uses a skill such as /sf-phase, a VS Code action, or an explicit CLI command.
  2. The CLI resolves the lifecycle subject
    The repository subject index maps the explicit ID, branch, or local selection to one Story. Ambiguous or missing state is rejected.
  3. The immutable phase contract is loaded
    The engine reads the pinned work type, active phase, template, inputs, gates, approval policy, write scope, and required world-model views.
  4. Context is composed and recorded
    The engine selects exact files and bytes, validates their hashes and freshness, renders the prompt, and records provenance under the Story context directory.
  5. Copilot handles ambiguity and authors
    The model may ask free-form questions, then proposes artifact content within the active phase's scope.
  6. The kernel rechecks live state
    Before publication, the engine recollects approved inputs, revalidates grounding, checks the active phase and branch, and scans artifacts.
  7. One governed commit is created
    The publication transaction writes state and projections, stages only an allowlist in a temporary index, creates the commit, advances the branch by compare-and-swap, and pushes normally.
  8. Review is a separate boundary
    Submission creates a reviewable state; an authorized human decision produces another lifecycle event and another publication.

Prompt composition and repository grounding

The prompt is not improvised from the chat history. It is a deterministic composition of the active contract and pinned evidence.

World model: repository facts, not instructions

The world model is generated repository evidence stored under singularity/world-model/. Its manifest declares every file, source commit, source-tree hash, views, task guides, and evidence ledger. The validator rejects missing required views, unsafe paths, symbolic links, malformed JSON/JSONL, empty files, duplicate declarations, and undeclared output files.

Freshness without false alarms

The source snapshot hashes application files while excluding Singularity-owned governance state, work-item state, initiative state, templates, world-model output, .git, and node_modules. Starting a Story or committing an approval therefore does not by itself make the repository model stale. Code or repository-content changes do.

Input collection algorithm

  1. Resolve declarations
    Find the producer phase and the exact artifact path from the immutable resolution.
  2. Inspect producer state
    The producer phase and registered artifact must both be approved unless the input is optional.
  3. Snapshot current bytes
    The live size and SHA-256 must equal the registered approved values.
  4. Bound injection
    Apply any configured byte ceiling without breaking UTF-8 and record whether truncation occurred.
  5. Render a managed block
    Nest approved content while neutralizing any producer input markers, so recursive phase chains remain unambiguous.
  6. Record provenance
    Write inputs-<phase>-gen<N>.json with producer generation, approver, hashes, bytes, status, and rendered-block hash.
  7. Recollect at publication
    Do not trust preparation. The live producer state, consumer block, and recorded hashes are checked again.

Five intent routers

Continue

Review a revision-bound action plan, select one current action, execute it through the kernel, and stop.

Inspect

Read status, progress, documents, prompt composition, reports, and next actions without mutation.

Review

Open exact artifacts and review packets, then make an authorized decision through the dedicated review path.

Recover

Diagnose pending publication or state inconsistency and follow a deterministic synchronization or repair action.

Administer

Diagnose configuration, workspaces, agents, Jira, state planes, and explicit repairs. Never inferred from ordinary chat.

Current implementation detail

The current worktreeHash hashes the output of git status --porcelain. It detects changes in the dirty-file set/status, but not a second byte-level edit that leaves the same status line. Treat it as a current freshness guard, not a full worktree content fingerprint.

Confirmation versus authorization

The kernel-provided action ID proves selection of an exact current action. High-value decisions still pass through the separate identity and approval-authority protocol; the action-plan confirmation by itself is not cryptographic proof of a human actor.

The publication transaction, Git isolation, and recovery

All lifecycle mutations converge on one transaction that treats the Git commit—not an in-memory mutation—as the durable boundary.

Why a temporary Git index matters

A contributor may have unrelated work staged. A normal git add would mutate that index even if a later commit used a path restriction. Singularity Flow instead builds a separate index from the expected HEAD, stages only the governed allowlist, writes a tree, creates a commit object, and advances the current branch ref with compare-and-swap semantics.

  1. Reject overlap
    If a governed path is already staged in the contributor's real index, publication stops rather than replacing or absorbing it.
  2. Build isolated tree
    GIT_INDEX_FILE points to a temporary index; read-tree, bounded add, and write-tree create the candidate tree.
  3. Create the commit
    commit-tree creates one parented commit and can use the configured signing key.
  4. Compare and swap
    update-ref advances the branch only if its old value still equals the expected HEAD; a race is rejected.
  5. Refresh only governed entries
    The real index is updated only for the committed governed paths. Unrelated staged content remains byte-for-byte staged.
  6. Publish normally
    The engine pushes HEAD:<branch> without force. Fast-forward rejection remains the cross-machine concurrency arbiter.

Capabilities connect organizational ownership and repository delivery; the ledger adds a tamper-evident proof plane without creating a competing runtime.

Capability policy fold

Declared contract versus verified conformance

The six contracts, verbatim, and what each one prevents

concise-relay

"Return the named CLI command output verbatim; do not elaborate, re-narrate, or hide errors." Prevents paid paraphrase — and the model softening an error into reassurance.

guided-actions

"Use read-only CLI evidence, preserve warnings and ordered actions, and change nothing unless explicitly requested." Guidance may narrate; it may not act.

explicit-selection

"Collect every required choice explicitly; never infer or preselect." Stops the subtlest failure: the model filling in defaults on the human's behalf. Convenience is not consent.

governed-review

"Show governed artifacts, hashes, identity warnings, and the exact confirmation before recording any decision." The approval ceremony cannot be shortcut or auto-filled.

clarification-and-artifact

"Use the complete governed prompt and approved inputs, ask unresolved questions, then publish and show configured artifacts." Ambiguity becomes questions, not assumptions.

deterministic-mutation

"Let the CLI validate and mutate state; preserve its exact result, warnings, publication status, artifacts, and next actions." The kernel decides; refusals are relayed faithfully.

Six contracts cover all eighty-eight skills because contracts track interaction shapes — relay, guide, choose, judge, author, mutate — not capabilities. Adding skill eighty-nine almost never means adding contract seven.

Token economics: zero-token core, metered generation

The platform treats model tokens like a metered utility. Determinism is not only a correctness strategy — it is the cost model: everything that can be computed is computed, and the model is paid only for judgment and prose.

L0 — zero-token core

Glossary of terms

Subject — anything the kernel can resolve and lock: a Story, Initiative, or Epic, addressed through the repository subject index.
Work item / Story — the unit of governed delivery; owns a canonical branch and a workflow.json.
Initiative / Epic — the portfolio unit above stories; append-only evidence, cross-repository orchestration.
Capability — an owned area of the system mapping to repositories; policy folds down its tree monotonically.
Workspace — a machine-local materialization of a capability's repositories; selects, never authors.
Phase — one stage of a work type's rail, with its artifact, template, gates, and approval requirement.
Generation — one governed model authoring pass inside a phase, numbered and recorded.
Immutable resolution — the SHA-256-pinned snapshot of config, templates, and agent taken at work start.
Projection — a derived, regenerable file (STATUS.md, summaries); never authoritative.
Plane — one of five state territories (definitions, lifecycle, local context, ledger, external observations).

Sequence gate — one of eight ordering/freshness checks; hard refuses, soft demands typed, audited consent.
Governance gate — the integrity check: hashes, documents, protected paths, stale approvals. No modes, no bypass.
Publication — the single kernel transaction that makes lifecycle change durable (lock → verify → write → isolated commit → CAS → push → ledger).
CAS ref update — compare-and-swap branch advance: succeeds only if the branch still points where state was loaded.
Pending publication — the machine-local recovery record after a failed push; blocks mutation until sync.
Outbox — durable intent for an external effect (ledger append, notification), replayed idempotently.
Idempotency key — deterministic identity (work·type·phase·generation·commit) making replays duplicate-proof.
Ledger — the orphan-branch, hash-chained, append-only proof plane; tamper-evident at T0, server-enforced at T3.

Agent — a governed, hash-pinned .agent.md shaping how generation approaches a phase; carries no authority.
Approval authority — a named human group (product, architecture, engineering, quality, design reviewers) empowered to approve; identity policy, not prompt content.
Behavioral contract — one of six stamped effect declarations telling the model what it may do with kernel output.
Skill — a thin Markdown adapter binding a slash command to a kernel call under a contract.
Action plan / envelope — kernel-emitted, content-addressed, revision-bound permission to execute exactly one action.
Receipt — one-time proof that a human saw and confirmed exactly what the kernel required.

World model — deterministic repository facts in seven views; grounding for generation, never instructions.
Grounding record — the recorded set of views and hashes a generation actually saw.
Light mode — the zero-LLM world-model build; digests at build-time cost, free at use.
Code graph — the deterministic module/dependency graph powering bounded structural queries and blast radius.
Clause — an addressable spec statement ([NS:REQ-001]); the unit of claim, coverage, and trace in the approved spec architecture.
Claim map — authored intent linking changes to the clauses they satisfy.
Trust tier — the ledger's enforcement rung: T0 tamper-evident → T3 server-verified transitions.

Security posture, trust boundaries, and current limitations

The design provides strong client-side lifecycle containment, but it is explicit about what still depends on deployment controls or future implementation.

Trust boundaries

Trusted coreNode kernel, pinned configuration, lifecycle branch, deterministic validators, bounded Git publication.
Governed but humanIdentity, approval groups, exact review, typed confirmations, change-request comments.
Untrusted evidenceModel prose, repository content injected into prompts, remote Markdown, external observations, advisory reports.
Deployment controlsBranch protection, signed commits, required checks, pre-receive or merge-queue validators, credential policy.

Current implementation boundaries

AreaCurrent statusOperational meaning
Lifecycle schema migrationNot implementedCurrent Story schema v2 and current Initiative schema are required; development state is recreated with factory reset.
Remote enforcementDeployment-dependentLocal kernel governs commands routed through it; T3 requires a mandatory server validator/pre-receive/merge-queue control.
Action plan worktree fingerprintStatus-shape hashCurrent implementation hashes porcelain status output rather than all dirty file bytes.
Action confirmationReview/selection guardKernel action ID is not a cryptographic human signature; decision authority is handled separately.
Skill behavioral conformanceDeclared and build-checkedModel responses are not yet automatically scored against every contract.
LedgerOptional and disabled by defaultLifecycle branch remains authority with or without the proof plane.
External systemsEvidence/write plansJira, CI, storage, and GitHub cannot silently become lifecycle authority.
Quality commandsTrusted repository configurationCurrent Story phase commands execute from pinned workflow configuration; artifact prose cannot inject them.
Clause-driven specificationsApproved future designP1–P5 are not current runtime commands or schemas.

Failure-containment map

Model drafts the wrong proseHuman review, artifact gates, and conformance can reject it; no lifecycle transition occurs merely because text was generated.
Model picks an invalid commandCommand registry, subject resolution, sequence gates, argument validation, and action-plan membership refuse it.
Concurrent user advances branchExpected HEAD, compare-and-swap ref update, and normal push rejection force reload/retry.
Remote push failsRetain exact local commit, write pending publication, block later mutation, synchronize later.
Ledger append failsLifecycle remains authoritative; outbox records the missing proof append for reconciliation.
Person bypasses CLI and pushes fabricated stateRequires hosting-side transition validation and branch protection to enforce against a malicious or compromised client.
No lifecycle migration framework

The current development line explicitly rejects unsupported or incomplete runtime schemas and instructs recreation. Do not promise long-lived production compatibility until deterministic Story and Initiative migration chains exist.

Security posture is tiered

Content hashes and local validation create integrity evidence. Protected branches, independent review, signed commits, and a mandatory server validator progressively strengthen who can publish trusted lifecycle transitions.

The safest way to operate the platform is to diagnose from authority, use narrow deterministic repairs, and let the publication protocol preserve history.

Safe operational order

  1. Inspect before repair
    Use status, nextsteps, doctor, state planes, and dry-run commands. Do not edit managed JSON by hand.
  2. Resolve authority first
    Confirm the exact Story/Initiative branch and current HEAD; local session or workspace selection can be recreated.
  3. Honor pending publication
    A retained local commit must reach its configured remote before another mutation.
  4. Repair projections narrowly
    Use state reconciliation only for declared projections. Never fabricate missing decisions or evidence.
  5. Rebuild evidence from authority
    World models and optional read indexes may be regenerated; lifecycle facts must come from the lifecycle branch.
  6. Run terminal verification
    Before declaring completion, execute the terminal gate and verify the remote head and required checks.

How it all works together

The platform is a chain of explicit responsibilities rather than a single autonomous agent.

What holds the system together

  1. Repository-owned configuration defines future work.
  2. Creation resolves and pins an immutable lifecycle contract.
  3. The CLI derives state and legal actions from that contract.
  4. Copilot authors against a deterministic, hash-recorded prompt.
  5. Gates verify sequence, context, scope, evidence, and authority.
  6. One publication transaction commits and transfers each mutation.
  7. Git branches carry shared operational truth across sessions and tools.
  8. Review packets, telemetry, events, and the optional ledger close the evidence loop.

Where to go next
